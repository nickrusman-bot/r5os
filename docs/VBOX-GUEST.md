## What the running guest already has

`scripts/run-vbox-r5.ps1` creates the VM with:

| Setting | Value | What the guest sees |
|---|---|---|
| Disk | PIIX4 IDE, fixed VDI | Haiku IDE stack |
| NIC | Intel 82540EM, bridged | `ipro1000` |
| Audio | Intel HDA | HDA driver |
| Mouse | USB tablet | absolute USB HID, not a Guest Additions pointer |
| Graphics | `vboxvga`, 16 MB VRAM | VESA / VBE framebuffer |
| Clipboard mode | disabled | not Devices → Shared Clipboard |
| Drag-and-drop | disabled | no host file drop |
| UART1 | `0x3F8` IRQ 4, server pipe `\\.\pipe\R5OS-clip` | COM1 |

The script does not define a shared folder, and it leaves VirtualBox clipboard mode and drag-and-drop disabled. The guest drivers are on the image. The product script still does not define a shared folder. When the host does offer one, sign-in mounts each share if `/dev/misc/vboxguest` exists.

Text clipboard is `distro/vboxclip` (`r5_vbox_clip`), started from the user launch job, plus `scripts/vbox-clipboard-host.ps1`. Frames are `R5C1` over `pc_serial1`. Unicode text, about 256 KB. `-NoClip` skips the host side. This is still the shipped path. The throwaway has passed one host-to-guest string and one guest-to-host string. The product script has not been switched.

The Haiku tree has no separate `VMMDev` source of its own and no VMware SVGA driver. `virtio_gpu` exists for QEMU. `app_server` paints software bitmaps (`BitmapDrawingEngine`). On VirtualBox the image can load `vboxvideo`; VESA remains when that device is absent. On the throwaway, Screen named the VirtualBox adapter.

Mouse movement in this VM already works (VirtualBox sessions through build 10013). That is the USB tablet. A second absolute pointer from Guest Additions would risk duplicate events. Do not add one until the tablet path is shown to be insufficient.

## What already exists elsewhere

Do not write a second Guest Additions stack from memory.

- Oracle still ships Haiku additions under `src/VBox/Additions/haiku` (VBoxMouse, VBoxVideo, VBoxTray, SharedFolders). VirtualBox **7.2.22** is **GPL-3.0-only** (`COPYING` and the Haiku makefile). Some IPRT files are GPL-3.0-only OR CDDL-1.0. The HaikuPorts 6.1.26 recipe's GPL v2 and CDDL is not this release. The source tarball and the cross-built ELF64 binaries sit outside this git tree. The daily image copies them on, with the GPL-3 text and the patch. Do not relicense them as MIT and do not paste them into MIT sources. Assessment: `docs/LICENSING.md`. Userspace programs ship as separate GPL-3.0 programs. Kernel modules ship in the MIT kernel because MIT allows that combination; the image also ships the GPL-3 text and the matching 7.2.22 source.
- HaikuPorts has `virtualbox_guest_additions` recipes through **6.1.26** (`ARCHITECTURES` includes `x86_64`, not gcc2). The 6.1.26 recipe was added as work in progress in 2021. It has not been built or booted on this R5OS image. Current VirtualBox hosts are newer than 6.1.26. Protocol compatibility is unproven.
- Older HaikuDepot additions did clipboard and time sync for some people. `vboxsf` was omitted from the gcc2 package because it panicked. Tracker on a shared folder has panicked the kernel before. On 2026-10-31 a current x86_64 build mounted one share from a shell. Tracker was not opened on it.

The published PCI device is vendor `0x80EE`, device `0xCAFE`. BAR layout, version word, events, and HGCM requests must be taken from the VirtualBox headers for the host version in use. Linux driver behavior is not the Haiku driver model.

## Controllers are not interchangeable

| Controller | Script today | Guest driver in this tree | Resize | 3D |
|---|---|---|---|---|
| `vboxvga` | yes, 16 MB | `vboxvideo`, VESA if that device is absent | one host hint on the throwaway | no |
| `VBoxSVGA` | no | none | no | no |
| `vmsvga` | no | none (no SVGA driver) | no | no |

Keep `vboxvga` until a modesetting driver for one of the others has booted to a desktop. Switching the script first can leave the guest on a blank mode.

VirtualBox 3D is a separate question. Detecting VGA, or a larger mode, is not acceleration. There is no Haiku driver here that submits commands to the host GPU through VMSVGA or VBoxSVGA. Leave 3D out of the guest-integration path.

## Order

1. **See the device.** On a running guest, `listdev` (or the PCI list in the syslog) must show `80EE:CAFE` before any driver claims it. Also record the display controller PCI ID. Seen on the 15:27 Europe/Amsterdam throwaway: `80ee:cafe` at bus 0 device 4, and `80ee:beef` at bus 0 device 2, before the driver line. `listdev` itself was not run.
2. **Identify only.** A native driver may claim `80EE:CAFE`, map its BARs, and log the version field from the VirtualBox structure for this host. No HGCM, no clipboard replacement, no resize. If the device is missing, boot continues on VESA and COM1. The 15:27 throwaway claimed the device (driver load after a successful attach). The version field was not logged. That driver is now part of the daily image. On 2026-10-31 around 12:04 Europe/Amsterdam the user booted that image in the GUI VM and said it works. The host listed Guest Additions 7.2.22 during that boot.
3. **One userspace service.** Time sync and guest version reporting share that device. The service exits when the device is absent. It must not block Login, Tracker, or Deskbar. On the 16:35 Europe/Amsterdam throwaway, `VBoxService` stayed up, `timesync` had already set the guest clock on the earlier boot, and the host listed `/VirtualBox/GuestAdd/Version` `7.2.22` plus `/VirtualBox/GuestInfo/OS/Product` `Haiku`. The serial log reached the first-login script with no panic. At 16:38 Europe/Amsterdam ProcessController showed Tracker, Deskbar, and `VBoxService` together. The service is installed on the daily image. On 2026-10-30 20:21 Europe/Amsterdam the same additions were booted in QEMU (`pc`, std VGA, no `80ee` device) from `generated/r5-os-vboxid-emptyout.raw`. The serial log lists PCI `1234:1111` and `1af4:1000`, `vesa_init()` succeeded, and `package_daemon` registered `/boot`. There is no `80ee`, no `vboxguest` load line, and no panic. `/boot/home/vbox-tray.log` then ends with `init -102` (`VERR_FILE_NOT_FOUND`): the tray started after `app_server` and did not open a guest device. The screen was not watched. `VBoxService` writes its log only after that open succeeds, and the log file was not updated. QEMU was stopped from the host. The VirtualBox window was left running.
4. **Clipboard.** Host and guest text, both directions, empty clipboard, and a large paste. On the throwaway, `R5OS-CLIP-IN` arrived in the guest and `R5OS-CLIP-OUT` arrived on the Windows clipboard. On 2026-10-30 18:52 Europe/Amsterdam the guest placed 32768 bytes (`R5OS-LARGE-0000` … `R5OS-LARGE-2047`) on the Windows clipboard. On 2026-10-30 19:56 Europe/Amsterdam an empty Windows clipboard arrived as a 0-byte guest file, and the same 32768-byte text arrived in the guest (`/boot/home/vbox-clip-large-in.txt`, 32769 bytes after `clipboard -p` added a newline), still there after ACPI S5. COM1 stays the shipped path until the product script is switched. File paste is later.
5. **Mouse.** Only if the USB tablet is wrong (capture, jumps, wrong coordinates after a mode change). One input path, through the input server. On 2026-10-30 19:16 Europe/Amsterdam, on the throwaway, movement, clicks, and scrolling worked. The pointer reached the edge of the guest screen and then moved on in Windows. No jump and no missed click were reported. No second mouse is added.
6. **Display.** One controller. Mode change without restarting `app_server`. Pointer coordinates after the change. A safe mode remains if the notification fails. On 2026-10-30 22:59 Europe/Amsterdam the throwaway Screen prefs said `Virtual display (VirtualBox Graphics Adapter)` at 1024×768, 24 bits/pixel, and the desktop was visible. Serial `generated/vbox-video3.log` loaded `drivers/dev/graphics/vboxvideo` for `80ee:beef` and did not panic. VESA still loads and remains the fallback when that device is absent. ## Tests that need someone at the machine

One sitting, on the throwaway VM only. Do not attach `generated/r5-os.vdi`. COM1 stays a file during these boots, so the COM1 clipboard helper stays off. The product script stays on COM1 until clipboard mode is switched on purpose.

3. One window resize of the VirtualBox window. Does the guest desktop follow without restarting, and does the pointer still land where it looks?
4. Shut down from the guest (not the host close button). If Windows then shows “unknown software exception (0x80000003)” for `VirtualBoxVM.exe`, leave the dialog up and say so. Clicking OK kills the host process. That dialog was seen once, on 2026-10-30 about 17:55 Europe/Amsterdam, after the guest had already entered ACPI S5. On the 19:16 sitting the user shut down from the guest and saw no Windows error. `showvminfo` afterwards said `powered off` (since 18:16:33Z), not `aborted`. 5. On 2026-10-31 10:54 Europe/Amsterdam the throwaway mounted `r5share` from a shell and copied one small file each way. Tracker was not opened on that share. Drag and drop is GitHub issue 89 and was not started. 3D was not tried.

## Tests that count

VMMDev present or absent, version negotiation, both clipboard directions, one resize, one shared-folder copy, reboot, and a boot with the device missing. QEMU does not stand in for this. The COM1 clipboard is already the tested path. Guest Additions features are not.
