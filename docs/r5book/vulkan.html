VK_RFIVE_view_surface

Vulkan in a window

A Vulkan program on R5 draws into an ordinary BView in a BWindow. The window can be resized, moved between workspaces, minimised and closed like any other. R5 has its own Vulkan extension for this, registered with Khronos.

How a frame reaches the screen

Each swapchain image has its own BBitmap. Present copies the image into it and makes it the view's bitmap. Your Draw() is not replaced. Lavapipe renders on the CPU; RADV renders on the GPU and copies the result into the bitmap.

vkCreateViewSurfaceRFIVE

function
typedef struct VkViewSurfaceCreateInfoRFIVE {
	VkStructureType                sType;	// VK_STRUCTURE_TYPE_VIEW_SURFACE_CREATE_INFO_RFIVE
	const void*                    pNext;	// NULL
	VkViewSurfaceCreateFlagsRFIVE  flags;	// 0, reserved
	BView*                         view;	// attached to a BWindow
} VkViewSurfaceCreateInfoRFIVE;

VkResult vkCreateViewSurfaceRFIVE(VkInstance instance,
	const VkViewSurfaceCreateInfoRFIVE* pCreateInfo,
	const VkAllocationCallbacks* pAllocator, VkSurfaceKHR* pSurface);

The create info carries the view and nothing else; the window is the view's window. The view must already be attached to a window. The surface keeps a BMessenger to that window, not a lock, so present may run on any thread. Destroying the surface does not destroy the view.

#define VK_USE_PLATFORM_VIEW_RFIVE
#include <vulkan/vulkan.h>
#include <vulkan/vulkan_r5.h>

const char* extensions[] = {
	VK_KHR_SURFACE_EXTENSION_NAME,
	VK_RFIVE_VIEW_SURFACE_EXTENSION_NAME,
};
// ... create the instance with these two extensions ...

VkViewSurfaceCreateInfoRFIVE info = {};
info.sType = VK_STRUCTURE_TYPE_VIEW_SURFACE_CREATE_INFO_RFIVE;
info.view = fRenderView;		// already AddChild()-ed to the window

VkSurfaceKHR surface;
VkResult result = vkCreateViewSurfaceRFIVE(instance, &info, NULL, &surface);

vkQueuePresentKHR

what it returns on R5

Present locks the window for at most one frame. It never makes the window's own thread wait.

SituationResultWhat your program does
ShownVK_SUCCESSCarry on.
The window was busy for a whole frameVK_SUCCESSNothing: that frame was skipped, the surface is fine.
The view changed sizeVK_SUBOPTIMAL_KHR, then VK_ERROR_OUT_OF_DATE_KHRBuild a new swapchain at the new size.
The window closed, or the view was removedVK_ERROR_SURFACE_LOST_KHRDestroy the swapchain and the surface.

The size in pixels is IntegerWidth() + 1 by IntegerHeight() + 1 of the view.

Present modes

VK_PRESENT_MODE_FIFO_KHR is the only mode offered today. It waits for the screen's retrace on the present thread. Asking for a mode the query did not return fails with VK_ERROR_INITIALIZATION_FAILED. Always pick from vkGetPhysicalDeviceSurfacePresentModesKHR.

GPU or software

Lavapipe can always present to a view. RADV says yes to vkGetPhysicalDeviceSurfaceSupportKHR only on a supported GPU with the radeon_hd setting gpu_present turned on; that setting is off by default for now. When RADV says no, the window runs on Lavapipe and looks the same. One line goes to the syslog the first time: RADV view surface: no, window through Lavapipe.

Do

Ask each device with vkGetPhysicalDeviceSurfaceSupportKHR and pick one that says yes.

Don't

Open RADV without asking. Creating the swapchain then fails with VK_ERROR_INITIALIZATION_FAILED; the device does not switch mid-frame.

Porting a program

A ported program creates a BWindow and a BView, then calls vkCreateViewSurfaceRFIVE where it would create a Metal or Wayland surface on other systems. vkcube from Vulkan-Tools and VulkanTeapot do exactly that. SDL, GLFW and other toolkits need a backend that does the same; it is this extension, not a second one.

Coming later. BVulkanView in the Graphics Kit will own the surface and the swapchain, call your Render() every frame, and rebuild the swapchain on its own. It is built on this extension and is not in R5 yet.
