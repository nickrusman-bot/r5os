Accounts and sessions

More than one person

R5 has accounts: one administrator and, if they want, standard accounts for other people. Someone signs in, works, locks the screen or logs out. A program does not draw those screens, but it runs inside that session, and a few things follow from that.

Who your program runs as

  • Your program runs as the person who signed in, never as root. The administrator, login name user, has a uid of 1000 or higher like everyone else.
  • Only the system services stay at uid 0: the kernel, launch_daemon, the registrar, the network and package services, and Login itself.
  • One graphical session runs at a time. There is no fast switching between people yet.

Folders and settings

Each person has their own home, Desktop and config/settings. Ask the system where they are; never write /boot/home into your program.

Do

find_directory(B_USER_SETTINGS_DIRECTORY, &path) for your settings, and getpwuid(getuid()) when you need the person's name or home.

Don't

Hardcode /boot/home/config/settings. For a standard account that is someone else's folder, and your program cannot write there.

BPath path;
if (find_directory(B_USER_SETTINGS_DIRECTORY, &path) == B_OK) {
	path.Append("MyApp settings");
	// /boot/home/config/settings/... for the administrator,
	// /boot/home/users/nicky/config/settings/... for Nicky
}

A setting that is for the whole computer lives in B_SYSTEM_SETTINGS_DIRECTORY, and only an administrator changes it.

Changes that need an administrator

Some changes are for the whole computer: the screen mode, the network, the clock, accounts. Do not run your program as root for them. In R5's own windows such a page is gray until the person opens the lock with an administrator password. Accounts are then changed by a small checked helper, not by the window running as root. One unlock covers every such page, and the grant ends at the lock screen and at log out.

No public call yet. The lock and the helper are used by Settings and Users & Accounts. A public call for other programs is not part of LibR5 yet. Until then, keep system-wide changes in those windows.

Lock and log out

Deskbar asks Login, by its signature, to lock the screen or to log out. A program can send the same message, for example a "lock" button in a remote-control app.

MessageToWhat happens
'lokc'application/x-vnd.Haiku-LoginThe lock screen covers the session. Programs keep running.
'lout'application/x-vnd.Haiku-LoginThe session ends. Deskbar asks the person first; a message you send does not.
BMessenger login("application/x-vnd.Haiku-Login");
if (login.IsValid())
	login.SendMessage('lokc');	// lock the screen

When the person logs out

Every program of the session gets B_QUIT_REQUESTED. Save what you need in QuitRequested() and quit. Do not open a dialog that waits for an answer: the person has already chosen to leave, and Login does not wait for it. The next person who signs in starts with a clean session.

Do

Save quietly, for example a draft next to the document, and return true.

Don't

Ask "Save changes?" and return false until someone answers. Nobody will.
